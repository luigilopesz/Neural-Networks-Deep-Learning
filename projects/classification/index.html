    2. Classification — Will this station flood tomorrow?¶

    Project: ASIA-FLOOD 25-Year Flood Risk Atlas · Task: binary classification · Target: flood_event_occurred on day t+1, for the same station

    Team: Luigi Lopes · Lucas Abatepietro · Marcelo Alonso

    The second delivery trains a neural network on the dataset of the EDA. It answers two questions. Does the network learn something that simpler models do not? And how far can the number it reports be trusted?

    Short answer. The MLP beats every baseline on the test set, in PR-AUC and in ROC-AUC. Its gain over logistic regression is real: about 3 times the variation between seeds. But the gain is small: +4.27 % in PR-AUC, against the +10 % we set as the success criterion before training. With only the measurements of the day itself, both models stop at a precision of about 8–9 % when they catch 80 % of the floods.

    Code. All code for this delivery is in code/:

    file role reads the test set?
    common.py imports the EDA's data.py and pipeline.py; metrics, the threshold rule, figure helper —
    model.py the network (PyTorch) and the training loop with early stopping —
    select_on_val.py steps 0–4: baselines, search and every choice, on validation no
    test_once.py steps 5–6: one evaluation on test, error analysis yes, once

    0. Starting point¶

    Pipeline. common.load_splits() imports data.py and pipeline.py from eda/code/ unchanged. The ColumnTransformer is fitted on the 310,500 training rows (2000–2016) only. Validation (2017–2020, 73,050 rows) and test (2021–2024, 73,000 rows) are only transformed. The result is the EDA's 21 features: 7 numeric, basin one-hot (10) and season one-hot (4). The leaky columns flood_risk_score and severity_level never enter.

    Split. The split is the EDA's chronological split, with seed 42. Validation is the last four years before the test window, so it never overlaps the test set. A random split would put near-copies of training days in the test set (EDA, Figure 1.5).

    split years rows floods rate base rate inside the monsoon
    train 2000–2016 310,500 6,566 2.1147 % —
    validation 2017–2020 73,050 1,620 2.2177 % 5.2941 % (30,600 monsoon rows)
    test 2021–2024 73,000 1,703 2.3329 % 5.5621 %

    Fixed before any training (and printed by select_on_val.py before the first model is fitted):

    • Main metric: PR-AUC (average precision). The task is 45 : 1 imbalanced, so accuracy is useless: "never flood" scores 97.78 % on validation. ROC-AUC and PR-AUC inside the monsoon are reported next to it.
    • Operating threshold: the highest threshold whose validation recall is still ≥ 80 %. Missing a flood (no warning, no evacuation) costs far more than a false alarm, so recall is fixed first. The report then states the precision that recall costs.
    • Success criterion: the MLP's test PR-AUC (mean of 3 seeds) is at least 10 % higher (relative) than the logistic regression's test PR-AUC.

    1. Baselines¶

    Three baselines are fitted on the same 21 pipeline features and scored on validation.

    baseline (validation) PR-AUC ROC-AUC threshold precision recall accuracy
    majority class (DummyClassifier("most_frequent")) 0.0222 0.5000 0.5 0.0000 0.0000 0.9778
    monsoon gate ("flood whenever monsoon_season = 1") 0.0529 0.7971 1.0 0.0529 1.0000 0.6033
    logistic regression (class_weight="balanced") 0.0776 0.8630 0.6734 0.0789 0.8000 0.7884

    Reading.

    • Majority class. It is the accuracy trap: 97.78 % accuracy, zero floods caught, and a PR-AUC equal to the base rate (0.0222).
    • Monsoon gate. It is the free calendar rule from the EDA (F3). It catches every flood but is right only 5.29 % of the time, which is exactly the monsoon base rate.
    • Logistic regression. It is the real reference. It lifts PR-AUC from 0.0529 (gate) to 0.0776. But at 80 % recall its precision is only 7.89 %, against the gate's 5.29 %.

    2. The network¶

    flowchart LR
    X["21 features<br/>(EDA pipeline)"] --> L1["Linear 21→64<br/>ReLU · Dropout 0.2"]
    L1 --> L2["Linear 64→32<br/>ReLU · Dropout 0.2"]
    L2 --> O["Linear 32→1<br/>logit"]
    O --> Loss["BCEWithLogitsLoss<br/>pos_weight = 46.29"]
    choice value why
    layers × units 21 → 64 → 32 → 1 Two hidden layers can model curved rules, such as a flood rate that peaks in mid-year (EDA F3), which a linear model cannot. The width halves at each layer, a small funnel. The search also tried one layer, 21 → 32 → 1.
    activation ReLU No saturation, so gradients do not vanish; and it is cheap.
    initialisation He (Kaiming) normal for the ReLU layers, Xavier for the output, biases 0 He keeps the activation variance stable through ReLU layers.
    output 1 unit, raw logit Binary task: one logit. The sigmoid lives inside the loss.
    loss BCEWithLogitsLoss(pos_weight=46.29) Numerically stable binary cross-entropy. pos_weight = negatives / positives in train handles the imbalance in the loss, with no resampling.
    parameters 3,521 = 21·64+64 + 64·32+32 + 32+1 88.2 training rows per parameter, so the network is far too small to memorise 310,500 rows.

    Code: model.py (python model.py checks the parameter count and that the same seed gives the same run).

    3. Training¶

    choice value why
    optimiser AdamW It adapts the step size per weight, which helps with the large gradients that pos_weight puts on the few flood rows. Its weight decay is decoupled, so the decay setting is exactly the regulariser compared in step 4.
    learning rate 1e-3 (3e-3 also tried) 1e-3 is Adam's standard value. 3e-3 peaked by epoch 3–11 and lost in the search (step 4).
    batch 1,024 That is about 21.7 floods per batch, so every step sees positives. It also gives 304 steps per epoch, which is fast on a CPU.
    epochs up to 60, patience 8 on validation PR-AUC Validation PR-AUC is noisy from one epoch to the next (0.0885 → 0.0853 between epochs 11 and 12, Figure 3.1b), so patience must span several epochs.
    seed 42 (initialisation, dropout masks, batch order) One CPU thread and deterministic kernels: a re-run gives identical numbers.

    Early stopping. After every epoch the loop measures validation PR-AUC and keeps a copy of the best weights. It stops after 8 epochs without improvement and restores the best weights. The chosen network peaked at epoch 18 and stopped at epoch 26.

    Figure 3.1. (a) Weighted BCE per epoch, both measured with dropout off. (b) Validation PR-AUC per epoch, with the logistic baseline (0.0776).

    epoch train loss validation loss validation PR-AUC
    1 0.7504 0.7733 0.0777
    18 (best, restored) 0.6609 0.6994 0.0893
    26 (last) 0.6544 0.7003 0.0863

    Reading.

    • Convergence. It converges: training loss falls every epoch, and validation loss falls until epoch 24 (0.6958).
    • Overfitting. There is no sharp onset of overfitting. The validation − training gap grows slowly, from 0.0229 at epoch 1 to 0.0459 at epoch 26. Validation loss stays flat after epoch 18 (0.6994 → 0.7003) while training loss keeps falling, which is where overfitting would begin.
    • Plateau. From epoch 11 on, validation PR-AUC stays between 0.0851 and 0.0893. The network stops improving because of what the 21 same-day features can say, not because it overfits. It is above the logistic baseline (0.0776) at every epoch, from epoch 1.

    Reading.

    • Architecture and learning rate. The two-layer network takes the top 6 places and 7 of the top 8. For the two-layer network, lr 1e-3 beats 3e-3 under all four regularisation settings; the faster rate stops improving early (best epoch 3 in three of the four). For the one-layer network, 3e-3 wins 3 of 4, because 1e-3 is slow for it (best epoch up to 47).
    • Dropout. It does not lower the gap at equal epochs; the curves in Figure 4.1b nearly coincide. What it does is keep the noisy validation curve climbing longer, so the run stops later (epoch 18 against 5) at a slightly higher peak.
    • Weight decay. It changes almost nothing at 1e-2.
    • Honest caveat. All four differences (+0.0005 to +0.0010) are smaller than the seed-to-seed standard deviation of validation PR-AUC, 0.0015 (step 5). With 88 rows per parameter, there is little overfitting for regularisation to remove. The choice of dropout is the rule ("best on validation") applied honestly, not evidence that dropout matters here.

    Chosen configuration: 21-64-32-1, ReLU, dropout 0.2, no weight decay, AdamW lr 1e-3, batch 1,024.

    The MLP on validation, before test.

    • The 80 %-recall threshold is 0.7731.

    5. Test evaluation¶

    test_once.py is the only script that loads 2021–2024, and nothing is chosen in it.

    • Seeds. It retrains the frozen configuration with seeds 42, 43 and 44. Each run uses early stopping on validation and the 80 %-recall threshold from validation.
    • Reproducibility check. Seed 42 reproduces the selected model exactly (an assert checks it).
    • Baselines. The baselines are refitted on train, with the logistic threshold also taken from validation.

    PR-AUC inside the monsoon equals the global PR-AUC to 4 decimals for every model but seeds 43/44 (0.0900, 0.0913), because the models rank the off-season days below the monsoon days. Seed 42 raises 0 alarms on the 42,400 off-season test rows.

    Was the criterion met? No.

    • The criterion. The MLP's mean test PR-AUC is 0.0900 against 0.0863 for logistic regression: a ratio of 1.0427, or +4.27 %. The criterion asked for ≥ 1.10.
    • Is the gap noise? The gap (0.0037) is 3.0× the seed standard deviation (0.0012), and all three seeds beat the logistic regression. So the network does learn something the linear model does not; it is just small.
    • At the operating point. At about 80 % recall the MLP's alarms are right 8.69 % of the time against 8.07 %. That means 10.50 false alarms per flood caught, against 11.40 for logistic regression (1,445 fewer false alarms over four years).
    • Validation was optimistic. Validation promised +15.03 %; test delivered +4.27 %. Part of that is selection: the best of 16 configurations on validation is optimistic by construction. This is why the test set had to stay untouched.

    6. Error analysis¶

    All on the test set, MLP seed 42, threshold 0.7731 from validation.

    Figure 6.1. Miss rate (1 − recall) and precision of the alarms (a) by basin and (b) by month (only months with floods; flood count in brackets). Conclusion: the errors are a calendar effect, not a geography effect. Every basin misses 11–31 % of its floods, but the October floods are missed 100 % (138 of 138) and June floods 95.45 % (22 floods), while July–August miss 6–10 %.

    pattern numbers hypothesis
    Edge-of-monsoon floods are missed October: miss rate 1.0000 (138 floods, 1 alarm); June 0.9545 (22). May, June and October hold 161 of the 1,703 test floods (9.45 %) but 160 of the 366 misses (43.72 %). In training, 95.58 % of floods fall in July–September and only 4.42 % (290 of 6,566) in June or October. The network learned a mid-year bump on day_of_year (step-6 importance, below). The validation threshold reaches 80 % recall using July–September alone, so the edge months sit below it. The missed floods are not dry days: their mean rainfall today is 57.8 mm against 38.3 mm for the floods caught. The network lets the calendar outvote the rain.
    The one off-season flood The worst miss, p = 0.000: ASIA_0016, Indus, 2021-05-22, rainfall 6.16 mm, soil moisture 24.87 %. This is the single flood in 25 years outside the monsoon flag (EDA F3: the gate catches 9,888 of 9,889). It looks like a dry spring day. No model built on these features can catch it.
    Basins differ only mildly Miss rate from 0.1098 (Salween) to 0.3077 (Brahmaputra); precision 0.0722–0.1025; PR-AUC 0.0664 (Yangtze) to 0.1167 (Helmand). Geography explains little, as the EDA found (F6: basin rates differ by 1.27×). With about 130–210 test floods per basin, differences of a few points are within sampling noise.
    Confident false alarms in early September, Salween The 5 worst false positives (p = 0.878–0.888) are all ASIA_0033–0035, Salween, 1–9 September, at 39–42 °C, with moderate rain (30–31 mm) and a low river (5.1–6.1 m). Peak-season date plus very high temperature, the 3rd most important feature, push the score up. Nothing in a single day says "the river is not rising"; a 7-day window of rain and river level would.

    Does it match the EDA?

    EDA said the network match?
    Geography is almost a null (F6) basin is the least important feature yes
    River level is redundant with rainfall (F5, Spearman 0.87) river level is 8th of 9 yes
    Rainfall, soil moisture and temperature carry next-day signal (AUC 0.80–0.84) 3rd–5th, all of similar size yes

    The one mismatch is the network's real contribution. A single-feature AUC only rewards a monotone relation: "more is riskier". The flood rate rises and then falls within the year (EDA Figure 3B.1), so day_of_year scores poorly by AUC. The MLP can bend it into a mid-year bump, which the logistic regression cannot. That bump is also what costs the June and October floods (table above). Permutation importance also splits credit between correlated features, so soil moisture, temperature and the monsoon flag share part of the same seasonal signal.

    7. Conclusion¶

    Was the network worth it? As a forecaster: only a little.

    • The MLP is better than logistic regression on every test metric, and by more than the seed noise: PR-AUC 0.0900 ± 0.0012 vs 0.0863, and 1,445 fewer false alarms at the same recall. But it falls short of the +10 % criterion fixed in advance.
    • As an analysis tool it was worth it. It found that the calendar, used non-linearly, is most of what a same-day model can learn. It also showed that the ceiling is the features, not the model: the network has 88 rows per parameter and barely overfits, and regularisation changed less than the seed does.

    Limitations.

    1. Same-day features only. The EDA pipeline has no windows (accumulated rain, rising river) or lags, which the project plan identified as the next step. Both models hit the same precision ceiling of about 8–9 % at 80 % recall.
    2. Synthetic data. No result here says anything about real floods.
    3. Uncalibrated scores. pos_weight inflates the outputs: the mean score is 9.9× the base rate. They can rank days and drive a threshold, but they must not be read as probabilities (Figure 5.3).
    4. One split in time. The +4.27 % comes from one four-year test window and three seeds.
    5. Regularisation choice. The search ranked 16 configurations by validation, on one seed. The top differences are smaller than seed noise.

    Who is affected by an error.

    • A missed flood falls on the people downstream: no warning, no evacuation, possible loss of life. Here that risk is concentrated in June and October, where the model is almost blind. An operator must be told this, or a calendar rule must cover those months.
    • A false alarm costs the agency and the public's trust. With about 10.5 false alarms per flood caught, alarm fatigue is a real risk.

    With more time.

    1. Add the window and lag features of the project plan (7-day rain sum, river slope, anomalies against the station's own normal) to the pipeline, with the same split.
    2. Set one threshold per month, or add a seasonal recall constraint, so June and October are not sacrificed to July–September.
    3. Calibrate on validation (Platt scaling).
    4. Compare with gradient boosting, which often ties with networks on tabular data.
    5. Repeat the search with 3 seeds per configuration.
